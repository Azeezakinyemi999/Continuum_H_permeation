config — study selection¶

How a study is selected¶

Every module in calculations/ imports its material data from calculations.config.model_config, which loads exactly one study. Which one is decided by location, first hit wins:

  1. $MHI_STUDY — a path to a study file, resolved from the repository root.

  2. study_config.py in the working directory, then each parent up to the repository root. This is how a notebook gets the study sitting in its own folder.

  3. Nothing else — there is no default. A run that named no study raises, listing the study folders it could have meant.

Each study folder’s study_config.py is the study: the material properties, operating conditions, sweep ranges and presets live there, not in the package.

calculations/config/model_config.py¶
# WHERE STUDIES LIVE
# =============================================================================
# There is no default study and no switch to edit. Each study folder holds its own
# study_config.py — the real input file, not a pointer — and that file is selected by
# running in its folder, or named explicitly through MHI_STUDY. Anything run from the
# repository root must name one; see _no_study_found below for why silence is worse.

# The filename a study folder must use. Deliberately NOT 'model_config.py': a notebook
# kernel has its own folder on sys.path, so a folder-local model_config.py would shadow
# a bare `import model_config` and give two different modules the same name.
STUDY_FILENAME = 'study_config.py'

# Override variable. Read once, at import.
STUDY_ENV_VAR = 'MHI_STUDY'

The study file is executed by path and its public names copied across by hand, because a star import’s module path is resolved at compile time and cannot be a variable. _load_active_study reproduces star-import semantics exactly, then validates the result against a 13-name REQUIRED_EXPORTS frozenset — raising ValueError naming both the study and the gap, rather than letting a missing export surface as an ImportError from deep inside calculations.sensitivity. load_study applies the same check, so reading a second study cannot enforce a weaker contract.

Everything derived from that study — the flat DEFAULT_PARAMS_* dicts, build_simulation_config, get_surface_kinetics_from_config and the plot styling — is defined in this module, below the namespace splice. It used to be duplicated verbatim in all four study files. The ordering is load-bearing: that block reads CONDITIONS, METALS and the rest as module globals, which exist only because of the globals().update() above it.

The choice is announced on stderr at import and recorded in ACTIVE_STUDY_NAME, ACTIVE_STUDY_PATH and ACTIVE_STUDY_SOURCE. A notebook that must have its own folder’s study calls assert_study_is_local in its first cell.

After changing study, run calculations.sensitivity.check_against_config(): preset yields, sweep ranges and draw counts were tuned for a specific material and are not automatically valid for another one.

Note

model_config populates its own namespace with globals().update() at import time, so METALS, OXIDES, CONDITIONS, DEFAULT_PARAMS_LEVEL5L6 and the rest are not statically defined there and therefore do not appear below. For their values see Complete Parameter Reference, which is generated against the active study.

calculations.config.model_config¶

Active study configuration.

This module is a LOADER, not a config. It loads exactly one study and re-exports its names, and everything else in the codebase imports from here:

calculations/*.py  ->  model_config  ->  the one active study

Each study IS a folder. <Folder>/study_config.py holds that study’s real input data — material properties, operating conditions, sensitivity ranges and presets — not a pointer to data kept elsewhere. Which study loads is decided by LOCATION:

  1. $MHI_STUDY — a path to a study file. For the container gate, the docs tools, CI, and any run that is not inside a study folder.

  2. study_config.py in the current working directory, then in each parent up to the repository root. This is the normal case for notebooks: a study folder holds its own config, and running a notebook in that folder uses it. No switch to flip.

  3. Nothing else. There is no default — a run that named no study raises, listing the folders it could have meant. A fallback would be taken by exactly the runs that never considered which material they wanted.

The working directory therefore decides the physics, and that is worth one moment of care: a notebook run from the wrong directory computes a different material than its folder implies. Three things guard against it — the one-line announcement on stderr at import, ACTIVE_STUDY_SOURCE recording HOW the study was chosen, and calculations.config.assert_study_is_local(), which notebooks call in their first cell to turn a wrong directory into a stack trace instead of a wrong number.

In VS Code, set "jupyter.notebookFileRoot": "${fileDirname}" or every notebook runs from the workspace root, where no study applies and the import fails. .vscode/settings.json in this repo does that. Jupyter Lab already uses the notebook’s own directory.

Restart any running kernel after changing which study applies: the binding happens at import time, so importlib.reload on a notebook module is not enough — the study’s dicts are already bound into calculations.sensitivity.

To add a study: make a folder, put its notebooks and a study_config.py in it. See calculations/config/__init__.py for the full recipe.

EXACTLY ONE study is ever loaded. This used to be a literal from studies.X import * with ACTIVE_STUDY as a separate label describing it, which let the two disagree — and they did: the label read one study while the import loaded another, and at one point BOTH studies were star-imported at once, so Python applied them in order and produced a hybrid. That state had Hastelloy N’s material dicts with Incoloy’s derived sensitivity parameters, and it moved L1 flux by a factor of ten while ACTIVE_STUDY still claimed Incoloy. The resolution order above has exactly one winner, and the winner is reported, so neither failure can recur.

After changing study, run:

from calculations.sensitivity import check_against_config check_against_config()

Preset yields, sweep ranges and draw counts were tuned for a specific material and are not automatically valid for another one.

calculations.config.model_config.load_study(spec)[source]¶

Load any study WITHOUT making it active, and return it as a module.

The supported way to read a second study — for a side-by-side comparison, or to pass another material registry to a property getter:

>>> other = load_study('Fuerst_et_al_2024/study_config.py')   
>>> get_metal_properties_at_T('Hastelloy_N_fuerst_2024', 900.0,
...                           metals=other.METALS)
Parameters:

spec (str or pathlib.Path) – Path to a study file. A relative path resolves from the repository root, not from the working directory, so the same call works from anywhere.

Returns:

The study, validated against REQUIRED_EXPORTS exactly as the active one is.

Return type:

module

Notes

This does not change what the solvers use. They bound their defaults at import time from whichever study was resolved then.

calculations.config.model_config.get_surface_kinetics_from_config(material_key, temperature_K, material_dict)[source]¶

Compute temperature-dependent surface kinetics from a METALS or OXIDES entry.

Uses the ‘surface_kinetics’ sub-dict within the material entry. Arrhenius form:

\[\begin{split}k_{diss}(T) &= k_{diss,ref}\exp\!\left[\frac{-E_{diss}}{R} \left(\frac{1}{T} - \frac{1}{T_{ref}}\right)\right] \\ K_{eq}(T) &= K_{eq,ref}\exp\!\left[\frac{-H_{eq}}{R} \left(\frac{1}{T} - \frac{1}{T_{ref}}\right)\right] \\ k_{recomb} &= \frac{k_{diss}}{K_{eq}}\end{split}\]
Parameters:

  • material_key (str   — key in METALS or OXIDES)

  • temperature_K (float — temperature [K])

  • material_dict (dict  — either METALS or OXIDES)

Returns:

dict

Return type:

k_diss, k_recomb, K_eq

calculations.config.model_config.build_simulation_config(metal=ACTIVE_METAL, oxide=ACTIVE_OXIDE, T_operating=None, P_upstream=None, L_metal=None, L_oxide=None, microstructure_overrides=None, defect_overrides=None)[source]¶

Assemble a solver-ready configuration dict for one metal/oxide pair.

Pulls the chosen entries out of METALS and OXIDES and merges them with the operating conditions in CONDITIONS, so a caller hands the model a single dict instead of threading a dozen parameters through by hand.

The oxide defect fractions in OXIDE_DEFECTS are also translated here into the per-path defect_config format the Level 3 solvers expect. A pinhole, crack or grain-boundary path is included only when its area fraction is non-zero, so setting a fraction to zero removes that transport path entirely rather than leaving a zero-weighted one in the parallel sum.

Parameters:

  • metal (str) – Keys into METALS and OXIDES. Default to ACTIVE_METAL / ACTIVE_OXIDE, which are the first entry of each dict.

  • oxide (str) – Keys into METALS and OXIDES. Default to ACTIVE_METAL / ACTIVE_OXIDE, which are the first entry of each dict.

  • T_operating (float, optional) – Override the corresponding CONDITIONS value. CONDITIONS is the only source for both thicknesses; the materials carry a sample_thickness recording the specimen their data came from, which is not the wall and is never read here. Note these use or, so a falsy 0 also takes the default — pass a small positive number instead.

  • P_upstream (float, optional) – Override the corresponding CONDITIONS value. CONDITIONS is the only source for both thicknesses; the materials carry a sample_thickness recording the specimen their data came from, which is not the wall and is never read here. Note these use or, so a falsy 0 also takes the default — pass a small positive number instead.

  • L_metal (float, optional) – Override the corresponding CONDITIONS value. CONDITIONS is the only source for both thicknesses; the materials carry a sample_thickness recording the specimen their data came from, which is not the wall and is never read here. Note these use or, so a falsy 0 also takes the default — pass a small positive number instead.

  • L_oxide (float, optional) – Override the corresponding CONDITIONS value. CONDITIONS is the only source for both thicknesses; the materials carry a sample_thickness recording the specimen their data came from, which is not the wall and is never read here. Note these use or, so a falsy 0 also takes the default — pass a small positive number instead.

  • microstructure_overrides (dict, optional) – Shallow-merged onto MICROSTRUCTURE and OXIDE_DEFECTS respectively. The defect overrides are applied BEFORE defect_config is derived, so they do change which paths exist.

  • defect_overrides (dict, optional) – Shallow-merged onto MICROSTRUCTURE and OXIDE_DEFECTS respectively. The defect overrides are applied BEFORE defect_config is derived, so they do change which paths exist.

Returns:

Material properties, operating conditions and sweep ranges, plus both the raw ‘oxide_defects’ block and the derived ‘defect_config’.

Return type:

dict

The files are structurally identical and define the same interface; they differ only in their values. STUDY_NAME is declared by the file rather than taken from the folder, so renaming a folder cannot silently relabel a result — and Application/ reports the 316L study it holds a copy of, which is why its reference set resolves.

Because a study is a file outside the package, it is not importable by a dotted name and is not documented by autodoc here. For its structure and the meaning of every block, see Complete Parameter Reference; to read one without making it active, use load_study above.
